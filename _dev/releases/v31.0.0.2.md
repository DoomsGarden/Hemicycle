## Funcionamiento para el jugador

Cuenta Google o acceso con correo/contraseña ya registrados. Perfil → Nube → revisar → tick → Activar guardado. Iniciar sesión no sube ni sustituye el progreso por sí solo. Después, los cambios persistidos de juego se guardan automáticamente, con estado pendiente/guardando/guardado/error. En otro dispositivo: misma cuenta → Perfil → Nube → revisar → tick → Recuperar copia. No se suman colecciones. Puede seguirse jugando sin cuenta ni vinculación.

Se sincroniza el respaldo versionado existente: ID de origen, colección y copias, FS, Elo, estadísticas, progreso/logros, Liga completa, enfriamientos de sobres gratuitos, recibos locales, estados de tutoriales y premios de temporadas pendientes/reclamados. El nick sigue siendo un dato separado de la cuenta. No se incluyen sesiones, claves ni tokens en los respaldos.

## Protección frente a pérdidas y conflictos

Tabla por auth.users.id, RLS propia, sin escrituras directas. RPC security definer con search_path vacío y validación de formato/tamaño/valores básicos; el cliente aplica la validación completa del catálogo y del respaldo. CAS mediante revisión y bloqueo FOR UPDATE, origen único entre cuentas y recibo de operación para reintentos tras perder una respuesta. Cada petición fija el token capturado de su cuenta; cambiar de sesión no puede enviar el guardado a una cuenta posterior por reutilizar el cliente del SDK.

La vinculación local pertenece a cuenta y origen, no al correo ni al nick. Abrir otra cuenta no sube automáticamente la colección anterior. Restaurar un archivo local o borrar progreso desactiva esa vinculación y cancela los efectos de respuestas antiguas en curso. No se vacía la nube al borrar datos locales.

Conflicto: conservar las dos copias para revisar. Se puede recuperar la nube o, tras revisión explícita, sustituirla por este dispositivo usando la revisión recién comprobada. No hay elección automática por reloj del cliente ni suma de saldos. Antes de recuperar se guarda una copia anterior local; antes de elegir el dispositivo se archiva la copia anterior cloud. Ambas descargas son por cuenta. La recuperación y sus metadatos se escriben juntos con rollback local si falla una escritura. Si cambian las copias durante la revisión, hay que revisarlas otra vez. Recuperar está bloqueado durante un combate o guía.

Desconexión: conserva los datos locales y el intento pendiente. Al reconectar o volver a la app comprueba revisiones y recibos antes de enviar nuevos cambios; hay reintento con espera tras errores para vinculaciones ya aceptadas. Al ocultar la app se intenta enviar lo pendiente. Cerrar abruptamente antes de confirmar una subida puede dejar cambios solo locales hasta la próxima apertura: el estado «guardado» indica confirmación del servidor.

## Límites de esta entrega

Es un respaldo del juego local del prelanzamiento. El servidor no calcula todavía partidas, FS, inventarios ni recompensas autoritativas, y no valida la legitimidad histórica de un archivo local editable. No habilita mercado real ni multijugador, no migra saldos competitivos y no prueba procedencia por conocer un ID. El SQL no borra tablas o filas preexistentes, es repetible y conserva perfiles y nicks anteriores. El correo/contraseña permite acceder a cuentas existentes; no añade registro o recuperación de contraseña por SMTP.

La conexión real a Google y las pruebas de usuarios se realizan por el propietario: el proxy del entorno bloquea llamadas directas al proyecto de Supabase. La integración automatizada usa el SDK oficial, transporte auth simulado y las **funciones SQL reales** en PostgreSQL embebido PGlite 0.3.14.
